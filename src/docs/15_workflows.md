# 작업 방식 — 감사·수정·검증·배포

이 저장소에서 에이전트(오케스트레이터와 서브에이전트)가 감사하고 고치고 배포할 때 따르는 절차다.
실제로 겪은 실패에서 나온 규칙이라, 규칙마다 **왜** 를 함께 적는다. 절대 규칙은 `CLAUDE.md` 가 우선한다.
원본 감사 프롬프트·결과는 공개 저장소에 두지 않는다(보안 감사 결과가 그대로 공개되고, 낡은 수치가
사실처럼 인용되기 때문이다). 남은 일은 `14_open_work.md`.

---

## 1. 역할

- **오케스트레이터**: 범위를 좁혀 나누고, 서브에이전트에게 맡기고, **결과를 코드와 실행으로 검증**한 뒤
  수정·커밋을 지휘한다. 직접 대부분을 감사하지 않는다.
- **감사자**: 읽고 추적해 발견을 보고한다. 저장소를 고치지 않고, `cargo`·`npm`·서버를 실행하지 않는다
  (빌드는 오케스트레이터가 돌린다). 재현 테스트는 임시 폴더에 초안으로 남긴다.
- **수정 에이전트**: 합의된 수정만 한다. 허용된 단일 테스트 바이너리만 돌리고 커밋하지 않는다.
- **검토자**: 수정 에이전트와 **다른** 에이전트가 미커밋 수정을 보고 APPROVE / REQUEST CHANGES 를 낸다.

**모델을 갈아 붙인다.** 구현·검토·감사에 같은 계열만 쓰면 사각지대가 겹친다. 의미·알고리즘 추론은
강한 추론 모델, 대조·전수는 다른 계열 — 수정과 검토는 반드시 다른 계열로.

**동시에 서브에이전트 1개, cargo 빌드 1개.** 이 머신은 자원이 모자라 병렬 빌드가 링크 오류(LNK1104)로
깨지고 PC 가 멈춘다. 빌드는 `CARGO_BUILD_JOBS=2`.

---

## 2. 감사자에게 주는 지시 (빠뜨리지 말 것)

- **발견을 만들어내지 마라.** 확신이 없으면 "미확인 — 테스트 필요"로 정확한 데이터와 함께. "결함 없음"은
  정상 결론이다.
- 예산의 절반~60% 를 쓰면 정리하고 **반드시 최종 보고서를 출력**하라. 못 끝낸 점검은 "확인 못 함".
- 발견마다 파일 + 함수 + 짧은 코드 인용 + **추적한 구체 시나리오**(데이터와 단계별 상태).
- 소유자 결정(`11_release_decisions.md`)은 결함이 아니다. 다시 올리지 않는다.
- 범위는 **아직 아무도 안 본 곳**과 **직전 수정**을 먼저. 이미 판정 난 구간의 전면 재감사는 낭비다.
  기각된 발견은 아무도 다시 보지 않으니 따로 재검토한다.

## 3. 등급과 처리

| 등급 | 뜻 | 처리 |
|---|---|---|
| **A-소유자** | 스키마 변경이 필요하거나 기존 설계·정책을 뒤집는다 | **고치지 않는다.** 모아서 소유자 판단을 기다린다 |
| **A-명백** | 누가 봐도 결함이고 소유자도 고치라 할 것이며 기존 DB·정책에 영향이 없다 | 선조치 후보고 가능 — 절차는 B/C 와 같다 |
| **B** | 작고 명확한 수정 | 아래 합의 절차 |
| **C** | 테스트 공백·문구·사소 | 아래 합의 절차. 수확 곡선을 본다 |

판단이 애매하면 A-소유자로 분류한다.

**B/C(와 A-명백) 선조치 합의 절차**
1. 감사자와 오케스트레이터의 판단이 같아야 한다. 다르면 오케스트레이터가 근거를 들어 반박하고,
   그래도 갈리면 에이전트를 하나 더 붙여 셋이 일치하게 조율한다.
2. **수정 에이전트**가 고친다.
3. **다른 에이전트(검토자)**가 APPROVE 해야 한다. 오케스트레이터 자기 검토로는 부족하다.
4. 오케스트레이터가 **변이로 판별력을 확인**한다(§5).
5. 전체 검증(§6) → 서명 커밋 → push → GitHub CI 확인.

**수정도 감사 대상이다.** 감사 지적을 고친 수정이 매번 새 결함을 낳았다(주석 한 줄이 마크업을 깨고,
한 경로만 막고 "고쳤다"고 하고, 문서를 "정밀화"하다 코드보다 강한 주장을 새로 만들었다). 그래서
**코드를 한 번이라도 고친 세션은 끝에 그 세션의 수정 전체를 대상으로 마감 감사**를 하고, CLEAN + APPROVE
가 나와야 끝난다. 마감 감사가 B 이상을 내면 고치고 다시 마감 감사.

**수확 곡선**: 앱 결함은 안 나오고 주석·문구 지적만 나오기 시작하면 새 범위 감사를 멈춘다. 더 하면
고치면서 만드는 결함이 찾는 결함을 넘어선다.

## 4. 같은 규칙을 두 번 구현한 곳은 등가 불변식으로 묶는다

자동 추천과 수동 추천 가드처럼 같은 규칙을 두 곳에서 구현하면, 시나리오 테스트만으로는 어긋남을 못 잡는다.
생성 구성에서 두 구현이 같은 결정을 하는지 보는 **불변식 테스트**를 둔다(`tests/auto_vs_manual.rs`).

- 존재(재현 가능)만 보지 말고 **전수**(수동으로 도달 가능한 모든 결과)와 대조하라 — 존재만 보던 불변식은
  "자동이 수동으로는 도달할 수 없는 결과를 확정"하는 결함을 놓쳤다.
- 생성기가 그 구조를 실제로 만드는지 **커버 카운터**로 단언하라. 편향 생성기가 필요할 때가 있다.
- 순서 민감한 재현 루프는 거짓 실패·거짓 통과를 낸다 — 가능하면 DFS 로 상태를 모은다.
- 어떤 변이는 불변식이 **구조상** 못 잡는다(예: 덜 확정하는 변이). 그 경우 시나리오·단위 테스트가 방어선이다 —
  헤더에 그렇게 적는다.

---

## 5. 변이로 판별력을 확인한다

"테스트를 추가했다"와 "방어선을 세웠다"는 다른 말이다. 새 테스트·새 가드는 대상 코드를 일부러 되돌려
**그 테스트가 실패하는지** 확인한다.

- 앵커는 짧게, **정확히 한 번** 치환되는지 먼저 확인한다. 긴 앵커는 공백 하나로 조용히 0건 치환된다.
- 복원은 `finally` 에서. 복원 뒤 원문(해시·`git diff`)을 확인하고 **mtime 을 올린다** — 백업 시점 mtime 으로
  되돌리면 cargo 가 재빌드를 건너뛰어 바이너리에 변이가 남는다.
- 판정은 **종료 코드 + 실패한 테스트 이름**. 출력을 자르지 마라 — 결과를 "마지막 N줄"만 남기다 다른
  바이너리의 실패 줄이 잘린 적이 있다.
- 변이가 엉뚱한 가드를 건드려 "다른 이유로" 실패하지 않는지 실패 메시지를 읽는다(예: 변이 코드에
  `unwrap_or` 를 쓰면 Fail-Fast 가드가 먼저 터진다 → `match` 를 써라).
- 변이 결과는 커밋 메시지와 테스트 머리 주석(판별력의 소재)에 **"확인함/예상"을 구분해** 적는다.

## 6. 검증

- 전체: `npm run ci`(프론트 vitest + `cargo test` + 오라클). 개발 중에는 `cargo test --test <파일>`.
- **vitest 는 종료 코드와 `Errors`/`Unhandled` 줄로 판정한다.** "Tests N passed" 줄만 보면 미처리 오류를
  놓친다 — 로컬 green / GitHub red 로 갈라진 적이 있다(원인은 테스트의 타이밍 비결정성).
- 의존성·빌드 설정을 바꾸면 `npm --prefix frontend run build` 도 본다.
- push 뒤 GitHub CI 를 끝까지 본다. 실행은 **워크플로 이름으로** 고른다 —
  `gh run list --commit <전체 sha> --workflow CI` → `gh run watch <id> --exit-status`. 같은 커밋에 Dependabot
  실행이 여러 개 생겨 최신 실행을 집으면 엉뚱한 것을 본다.
- `cargo run`·`npm run dev` 로 띄워 확인하지 않는다. 브라우저 실측이 꼭 필요하면 dev exe 를 임시 폴더로
  복사해 격리 DB 로 띄우고 API 로 시드한다(개발 DB 를 건드리지 않는다).

## 7. 문서·주석 (CLAUDE.md 규칙 9 의 실무)

- 세어서 얻은 수치(테스트 개수·호출 수·건수)와 줄 번호를 쓰지 않는다. 필요하면 재현 명령(`git grep …`)을 적는다.
  재현 명령도 실제로 그 대상을 찾는지 확인한다(`require_cols` 로 세면 조건부 `get_col` 경로를 놓쳤다).
- 주석·명세가 코드보다 강하게 주장하지 않게 한다. 확인하지 않은 것은 "…로 보인다", "확인하지 않았다".
- 기록용 테스트는 "기록이지 방어선이 아니다"라고 밝히고, **현재의 불완전한 동작을 단언으로 고정하지 않는다**
  (고칠 때 방어선이 아니라 장애물이 된다).
- 사용자에게 보이는 안내 문구에는 처방(예: "미선발하세요")을 함부로 넣지 않는다 — 처방이 틀리는 구성이 있었다.
  상태(사실)만 적는다.

## 8. 커밋·배포

- 커밋은 **GPG 서명 필수**(우회 금지). 비대화형 셸에서 서명이 타임아웃하면 소유자에게 암호 캐시를 요청한다.
- 커밋 메시지는 한국어로 무엇이 왜 틀렸는지와 변이 결과. **`Co-Authored-By` 줄을 넣지 않는다.**
- 논리 단위마다 커밋(백엔드 / 프론트 / 문서).
- 배포: 태그는 GPG 서명 annotated. 배포 전이면 태그를 옮길 수 있다(`git tag -f -s -a` + 원격 강제 push).
  `publish.yml` 은 **태그 ref** 에서 수동 실행하고(master 에서 빌드하지 않는다) draft 릴리스를 만든다.
- 릴리스 본문은 CHANGELOG 절을 그대로 붙이지 않는다. 직전 릴리스 본문을 받아 골격을 맞추고, 제품 소개·
  설치·라이선스·피드백 절은 그대로 옮긴다(zip 버전만 교체). 공개(Publish)는 소유자가 한다.

---

## 9. 의존성

`npm update`(semver 범위 안)로 패치하고 `npm run ci` 가 green 이면 커밋한다. red 이거나 메이저가 필요하면
지금 하지 않고 다음 의존성 주기로 미룬다. "이 경보는 우리와 무관하다"를 분석하기 전에 "그냥 올릴 수
있나"부터 본다.

---

## 10. 사용량·중단

- 긴 감사는 사용량 한도에 걸린다. 감사 하나가 끝날 때마다 사용량을 보고, 한도에 가까우면 리셋 뒤로 재개를
  예약하고 멈춘다. 재개에 필요한 상태(다음 할 일·결정·커밋)를 임시 메모 파일에 정확히 적어 둔다.
- 소유자가 자리를 비우면 질문은 시작할 때 한 번에 한다. 소유자 판단이 필요한 것(A-소유자)은 모아서 보고한다.
